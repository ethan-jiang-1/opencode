# 1.3 `Tools` Registry 注册机制与工具沙箱

要让 Agent 具备改变世界的能力，就必须长出四肢。在 OpenCode 中，“四肢”被抽象封装成了严谨的 `Tool`。你可以在 `packages/opencode/src/tool/` 目录下找到海量的内置能力实现。

但从架构的上帝视角来看，这些零散的工具（Bash、Read、Write...）是如何有组织、有王法地被 LLM 所调度和拦截的呢？

## 🔬 Tool 接口标准模型

每一个能被注册进 Agent 的工具，都必须严格遵守 `Tool.Interface` 的核心定义：

```typescript
export interface Tool<A = any> {
  // 核心定义：这个工具必须要经过系统哪条权限体系的拷问？
  permission: ToolPermission | ToolPermission[] | ((args: A) => ToolPermission | ToolPermission[]);
  
  // Zod 强校验的入参结构。绝不把脏数据喂给原生系统。
  parameters: z.ZodType<A>;
  
  // 这就是生成向大模型（OpenAI 等）宣称能力的描述语。
  description: string | ((args: { path: { cwd: string; root: string } }) => string);
  
  // 执行本体。注意包裹了 Session、Agent 和 MessageiD 等庞大的上下文信息
  execute: (
    args: A,
    options: {
      sessionID: SessionID;
      abort: AbortSignal;
      messageID: MessageID;
      agent: string;
      messages: ModelMessage[];
      // ... 提供向外界请求协助或询问（Human-in-loop）的渠道
      ask: (question: string) => Promise<string | undefined>;
    }
  ) => Promise<Tool.Result>;
}
```

## ⚙️ Registry: 动态路由与剥离

在 `prompt.ts` 将对话流送给 LLM 前，有一步至关重要的函数：`resolveTools`。
这不只是简单的 `$import`，这实际上是一个强大的过滤网（Filter Matrix）。

1. 引擎会拉出所有的全局内置 Tools。
2. 引擎拉取发报者（比如当前激活角色是 `explore` Agent）的 `Permission.Ruleset`。
3. 把所有的 Tool 倒进这层筛子：
   - 过滤掉被明确 `deny` 或者默认不在白名单的能力。
   - 如果某个工具强依赖特定的参数校验，动态分析决定是放行还是需要挂载前置审批 (`ask`)。
4. 将剥离出的大名单，组装成给大模型侧的 `functions/tools` API Payload，从而将这些沙盒内的可用工具推给模型。

## 🛡 执行期的沙箱隔离保护

在之前的架构里，如果是脚本语言调用子进程或读取文件异常爆掉，整个应用可能就垮了。
在这里我们看到，由于整个 Loop 包裹在了 Effect 框架里，Tools 的 `execute` 被设计成绝对安全的防空洞：

- **自愈机制 (Self-Healing)**：当大模型写出一个错误的 bash 命令，引发了 Exit Code 非 0 或是 `FileSystem` 读写异常，工具自身或 `Processor` 的 Wrapper 捕获报错后，它**不是选择 Crash 崩溃**，而是生成一个 `ToolResultPart` 包含着极大量的 Error Stack Trace（堆栈/明细错误），并将 `finish` 设为空要求大模型再来一遍。
- **这教会了 Agent 什么是“探索”。**

## 💡 Harness 启示：如何无感“开挂” (Cheats)？

Harness 开发最核心的实战范例：假设公司有一套极复杂的云原生发版脚本 `/usr/local/bin/deploy.sh`，你不想依靠 Agent 用 Bash 一遍遍猜怎么用。

**高级解法：自定义专属 Tool。**

向 Registry 里注册一个 `ShipToCloud` Tool:
```typescript
{
  permission: { permission: "shiptocloud", action: "ask" }, // 高危动作，要求人类批准
  parameters: z.object({ env: z.enum(["staging", "prod"]), component: z.string() }),
  description: "Deploy current component to the specified cloud environment using company standard pipelines.",
  execute: async (args) => {
    // 你的 Harness 底层逻辑封装，无需告知大模型细节。
    return { output: `Component ${args.component} deployed successfully.` };
  }
}
```
通过向系统底层做如此优雅的注册，大模型就能在循环中获得一个专用的、参数校验严格的方法论。这就是增强 Agent 最正统（Orthodox）的做法。
