# 1.1 `Agent.Info` 与权限边界 (Agent State & Permissions)

在 OpenCode 的底层世界里，必须彻底破除一个执念：“Agent 就是一段 System Prompt”。
这是一个由强类型约束的状态机。在 `packages/opencode/src/agent/agent.ts` 的源码中，我们可以清晰地看见它的真面目：一个拥有数据形态 (`Schema`)、权限矩阵 (`Permission.Ruleset`) 和身份特征的实例配置。

## 🔬 源码解剖: `Agent.Info`

看看底层是如何通过 `zod` 严格定义一个 Agent 的（源码提取）：

```typescript
export namespace Agent {
  export const Info = z.object({
    name: z.string(),
    description: z.string().optional(),
    mode: z.enum(["subagent", "primary", "all"]),
    native: z.boolean().optional(),
    hidden: z.boolean().optional(), // 极其关键的隐身模式
    permission: Permission.Ruleset, // Agent 真正的躯干：权限网
    model: z.object({
        modelID: ModelID.zod,
        providerID: ProviderID.zod,
    }).optional(), // 可选覆写底层大模型
    prompt: z.string().optional(),
    steps: z.number().int().positive().optional(),
  })
}
```

注意这几个核心字段的意义：
- **`mode`**: 决定了这个 Agent 的层级定位。`primary` 意味着它是用户从外界显式调用的主力脑区（例如内置的 `build` 或 `plan`）；`subagent` 意味着它是为主模型打工的分身（例如内置的跨目录检索专家 `explore`）。
- **`hidden: true`**: 有些 Agent (例如负责上下文压缩的 `compaction`) 对外部世界是完全不可见的。它只在 `runLoop` 底层的心跳中被幽灵般唤醒并处理残骸。这给了我们在写 Harness 极大的启发：**用不可见的 Agent 洗数据**。
- **`permission`**: 最重要的拦截边界。

## 🛡 不可逾越的壁垒 `Permission.Ruleset`

传统基于自然语言指令的 Agent，在遇到死循环/高危动作时，极大概率会退化并“突破”Prompt 指令的防线。
所以，最好的 Harness 是**物理切断执行流**。

在 OpenCode 中，不同的权限 (`allow` / `ask` / `deny`) 构建了内置角色的围城：

```typescript
// default (兜底默认网段) —— 定义了整个系统的基座规则
const defaults = Permission.fromConfig({
  "*": "allow",
  doom_loop: "ask", // 一旦系统检测出循环报错行为，强制弹出让人类确认 (Human-in-the-loop)
  question: "deny",
  plan_enter: "deny",
  "*.env": "ask", // 即便有了全部允许读写，触碰环境变量凭证必须拦截
})

// 内置 [plan] Agent —— 极度的保守主义者
permission: Permission.merge(
  defaults,
  Permission.fromConfig({
    edit: {
      "*": "deny", // 所有的写动作，全部拉闸
      ".opencode/plans/*.md": "allow", // 唯一的赦免点，只能在此处留痕
    },
  })
)

// 内置 [explore] Agent —— 唯一的猎犬
permission: Permission.merge(
  defaults,
  Permission.fromConfig({
    "*": "deny",     // 不许做任何操作
    grep: "allow",   // 只能搜
    glob: "allow",   // 只能列文件
    read: "allow"    // 只能读
  })
)
```

## 🧠 设计哲学 (Architectural Insights)

作为一个进阶开发者，当我们试图给这个 Agent 添加新能力或构建外围 Harness 时：

**永远先想 Permission，再想 Prompt。**

举例：如果公司需要部署一个专注于分析第三方库漏洞的 Security Agent。
❌ 错误的打法：在设置里加上 `System Prompt: "你是一个安全特工，只能读 nodes_modules，不能改 src 里的任何文件"`。
✅ 架构师的打法：向 `agent.ts` (或外挂配置文件) 注入：
```json
{
  "name": "security",
  "permission": {
    "edit": {"*": "deny"},
    "read": {
      "src/**/*": "deny",
      "node_modules/**/*": "allow"
    }
  }
}
```
通过系统底层物理截断（在 `Processor` 解析工具参数时直接抛错拦截），才是大型工业级 AI Client 的正道。
