# 4.3 终极杀器：Subtask 与多智能体管弦编排 (Agent Orchestration)

一个复杂如重构微服务，或分析数十个组件安全漏洞的任务，是不可能依赖在单向的 `while(true)` Loop 中一遍遍生成数十万词元的对话流来解决的，这相当于让一个智者在一张挤满字的草稿纸上强行证明拓扑论定理一样荒谬。

如果说 Hook, Skills, MCP 都是在给这个智者传递更优秀的笔和计算器。那么这一章，我们将教会它拥有 **“创造克隆分身”和分配流转节点的能力**。

这就是最顶级的 Harness 设计：**主次从属的编排体系 (Agent Orchestration / Supervisor pattern)**。

## 🎭 `SubtaskPart` 的诞生之旅

这一切在 `prompt.ts` 的 `runLoop` 循环判定前段，有几行轻描淡写但能量惊人的代码：
```typescript
const task = msg.parts.find(p => p.type === "subtask");

if (task?.type === "subtask") {
    yield* handleSubtask({ task, model, lastUser, sessionID, session, msgs })
    continue
}
```

这就是 "多脑协同" (Agent-in-Agent Loop) 的枢纽。这意味着在一个庞大、高维的 Agent (例如具有全部规划和读写权限的主管 `plan` / `build`) 在一通分析之后，发现前方有大量的脏活、且只需要非常聚焦的思维带宽时，大模型在生成 JSON 时不调用常规的改文件操作。

它生成了一个特有的返回区块 `subtask`！

## 👨‍🏭 实战推演：如何利用 Subtask 解决复杂工程

如果我们将这套理念落地到一个架构改造项目中，它的形态如下：

1. **主理人阶段 (The Orchestrator)**：
   我们启动高权限、全局感知的 `plan` Agent（即系统里的架构师角色）。
   用户向它扔过去一个极尽庞大的 Markdown 需求档：“请在 4 个子包里全部加上 Redis 缓存鉴权层”。

2. **分解与发射 (Spawn)**：
   在 Harness 的编排下，主管 Agent 根据解析，使用它的工具箱。它向 `runLoop` 底层抛出 4 个并行（或串行）的 `SubtaskPart` 请求信标。它告诉底层：“请召唤出我专门用于阅读和爆破极短代码行的猎犬分身，例如一个低级但极快的特定 `subagent`，携带这**极度聚焦**的前置要求，去解决那几个包的鉴权代码改写。其他的全部不要让它看。”

3. **进入 `handleSubtask` 独立宇宙**：
   系统引擎拦截了这个要求。在这瞬间：
   - 为这 4 件分出去的杂事，重新建立了 4 个物理隔离的、上下文异常干净（只有一行改写要求和部分代码库路径）的新 Session 环境。
   - 新环境里的 Agent 完全没有此前主理人分析上万字需求文档的冗长记忆负担 (Context Loss 消除)。
   - 子 Agent 开启自己短暂的 `runLoop` 循环。由于目标绝对精确且背景知识少，大模型不仅 API 推理飞快拉满，幻觉概率降至最低甚至趋于 0。它的唯一任务，可能就是打开某个文件，精准到 `L42~L55`，替换掉旧逻辑。

4. **回收与主位继承 (Summary & Merge)**：
   子工作流跑完了，或者它失败并在自己的小单间里卡死了。
   最后的信息不论好坏，被凝聚成一段精华（往往通过我们上章分析过的一句话带 `summary` 的汇报消息），返回推入原来主管 Agent 的那一组庞大对话历史（`msgs`）里的新部位！
   主理人醒来，继续它的主回路循环。
