# 4.6 终极解答：如何将外部 CLI 软件的能力注入系统 (超越 Function Call)

你提到了一个极其敏锐且触及 AI Agent 灵魂的问题。

> *“现在有些新软件想靠 CLI 把能力注进去，原来有个叫 Function Call (方生靠) 的东西，但好像不太像... OpenCode 代码里哪一块支持这个事？怎么具象化？”*

你的直觉非常准这就是目前大模型架构设计的最高分水岭：**如何优雅地把一个由别人写好的 CLI 工具（例如 `kubectl`, `aws-cli` 或某个私有的 `deploy-bot`）变成大模型的“原生四肢”？**

在 OpenCode 中，这块代码的真正操盘手在 **`packages/opencode/src/tool/registry.ts` 和 `packages/opencode/src/tool/tool.ts`** 里。

## 🔬 源码解剖：能力是如何被凭空“吸”进去的？

翻开 `tool/registry.ts` 的第 88~102 行，你会看到一段非常残暴的动态挂载逻辑：

```typescript
// 源码级萃取：动态获取自定义工具
const dirs = yield* config.directories(); // 读取当前用户工作区
// 物理扫描用户的目录寻找扩展文件
const matches = dirs.flatMap((dir) =>
  Glob.scanSync("{tool,tools}/*.{js,ts}", { cwd: dir, absolute: true, dot: true, symlink: true }),
);

for (const match of matches) {
  // 核心！利用 Node 的 dynamic import 直接把你写的 js/ts 拉进内存
  const mod = yield* Effect.promise(() => import(match));
  
  for (const [id, def] of Object.entries<ToolDefinition>(mod)) {
      // 包装并注册进主循环的大名单中！
      custom.push(fromPlugin(id === "default" ? namespace : `${namespace}_${id}`, def));
  }
}
```

这意味着：**OpenCode 默认自带了一个“热插拔”的夹层**。你不需要去修改 OpenCode 自己的源码，只需要在你的项目根目录下建一个 `.opencode/tools/` 文件夹。把你的能力丢进去，它就会在启动时被“吸”进引擎。

## ⚔️ 深度对比：凭什么说它比原始的 "Function Call" 强？

你提到的 **方生靠 (Function Call)**，是 OpenAI API 提供的底层协议（告诉大模型“我有个叫 X 的参数规则为 Y 的函数”）。
但在纯天然手敲的 Function Call 环境里，你极其痛苦：
1. 你要把参数写成难以维护的 JSON Schema。
2. 大模型返回 JSON 给你的代码时，你得自己写个 `if...else` 去解析。
3. 如果大模型把参数写错了（比如少传了必填项），你的程序会直接 Crash（崩溃）。

**OpenCode 的设计 (`packages/opencode/src/tool/tool.ts`) 彻底接管了这种痛苦！**
它在第 62 行左右，做了一个极其优雅的拦截：

```typescript
// tool.ts 中对于 Function Call 返回值的沙箱拦截
try {
  toolInfo.parameters.parse(args) // 强制使用 Zod 校验大模型传过来的参数！
} catch (error) {
  // 如果大模型写糊涂了参数传错，系统不会崩溃，而是自动拼接一段报错退回去！
  throw new Error(
    `The ${id} tool was called with invalid arguments: ${error}.\nPlease rewrite the input so it satisfies the expected schema.`
  )
}
const result = await execute(args, ctx)
```
在这个机制下，它把原始粗糙的 Function Call，包装成了一个具备**Zod 强类型校验、自动序列化、且自带报错自愈 (Self-Correction)** 的高级沙箱！

## 💡 落地具象化：给一个实战案例

假设你们团队刚买了一个新的服务器运维 CLI 软件，叫 `k8s-rocket`。传统的方法只能祈祷大模型在 bash 里学会敲这个新命令，经常出错且带入安全隐患。

**在 Harness 架构下，我们将其包装为原生注入能力：**

在项目的 `.opencode/tools/rocket.ts` 中写下以下代码：
```typescript
import { z } from "zod";
import { execSync } from "child_process";

// 导出一个遵循 OpenCode 标准定义的 ToolDefinition
export const deployNode = {
  // 这个 description 就是最后投喂给大模型看到的那段 Function Call 提示词
  description: "Use this capability exclusively to trigger k8s-rocket deployment for a specific node CLI tool.",
  
  // Zod：极其严苛的打卡机，大模型不按这个格式输出，底层的 tool.ts 就会把它打回去重写
  parameters: z.object({
    nodeName: z.string().describe("The specific target node name, eg: 'worker-node-1'"),
    force: z.boolean().default(false).describe("Whether to force restart the pod")
  }),

  // 这里真正执行你的外部 CLI 能力
  execute: async (args, ctx) => {
    // 此刻，哪怕外界 CLI 再复杂，对于大模型来说，它只填了 nodeName 和 force 两个参数
    const flag = args.force ? "--force" : "";
    
    // 我们在这个暗箱里执行那个危险或繁琐的新软件 CLI
    const output = execSync(`k8s-rocket deploy ${args.nodeName} ${flag}`).toString();
    
    // 将能力的结果打包，顺着 registry.ts 注册的通道回传到大模型的 RunLoop
    return {
      title: "K8s Rocket Execution",
      output: `Deployment successfully triggered. System log: \n${output}`,
    };
  }
};
```

### 看懂它有多可怕了吗？

当你把这个文件往目录里一放，启动 OpenCode 时，`registry.ts` 的 `all()` 函数就会把 `deployNode` 吃进去，和基础的 `bash`、`edit` 一并送到前线。

**此时，大模型的思考回路变了。**
当用户说：“帮我把挂掉的一号节点重启一下。”
大模型原本可能试图去用内置的 `bash` 敲乱七八糟的脚本。而在注入之后，它看到了 `deployNode` 工具（Function Call）。它会立刻生成一串 JSON ：`{"name": "rocket_deployNode", "arguments": { "nodeName": "worker-node-1", "force": true }}`。

**外部的、繁杂的、未知的“新 CLI 软件”，就通过这段短小精悍的胶水层，变成了大模型身体里最原生、防呆（Zod）、自愈的一条胳膊。** 这个机制，正是高级 Agent 引擎对于第三方能力收编的核心终极答案。
