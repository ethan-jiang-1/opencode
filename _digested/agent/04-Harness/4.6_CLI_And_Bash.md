# 4.6 最危险的双刃剑：CLI 与 Bash 工具的执行注入

我们探讨了所有的智能挂载（Skill, MCP, Hooks, A2A），现在应当回到最原生、最强力的赋能终端：**操作系统底层的 Shell/Bash。**

在 OpenCode 中，CLI 接口与 Bash 工具组成了系统落地干活的终端。如果将 Agent 比作一个聪慧的大脑，那 `bash.ts` 和各种终端指令就是它最孔武有力、但也最需要加以管束的双臂。

## 🔬 OpenCode 是怎么处理 Bash 代码的？

这是源码中最具硬核防御设计的部分之一（参见 `packages/opencode/src/tool/bash.ts`）。

因为我们在使用 Agent 时，常常要求它在复杂的 OS 环境下作业。而一旦它开始疯狂打字：
`rm -rf /`，或者是 `git reset --hard`，系统该如何抵御？

1. **Tree-Sitter AST 前置解析 (解析比执行先行)**
   一般的低端 AI 脚本，收到模型输出的 `echo "hi"` 就丢给 Node.js 里的 `child_process.exec()`，听天由命。
   在 OpenCode 这个成熟的平台上，当大模型输出 `bash` `tool-calls` 参数时，底层 `bash.ts` 首先调用了 `tree-sitter` (一个极其强大的编译器前端 AST 解析库)！
   ```typescript
   // 伪逻辑
   const root = await parse(params.command, ps);
   const scan = await collect(root, cwd, ps, shell);
   // 扫描该命令行试图触碰的一切目录、读写动作、命令关键词（如 rm, push-location 等）
   ```

2. **Permission Check (与 `Agent.Info` 打通的死亡拦截)**
   如果 `tree-sitter` 解析出模型实际上是要执行一个文件删除动作 (`FILES.has(cmd)`)，但它所指的参数目录 `scan.dirs` 明显超出了该 Agent 在初始化时所设定的 `Workspace` 的法定边界。
   底层 `ask()` 机制将瞬间在沙箱内把这个进程钉住（挂起在 Prompt 控制台上），并将权利交给最原初的发起人（Human Terminal）审慎判定。

3. **流式截断与兜底 (Self-Correction from stderr)**
   在跑比如 npm 甚至大型 docker 构建时，由于输出高达十几 MB。
   普通挂载的做法可能导致 Agent 立刻被垃圾日志噎死（Out of Context Window）。
   OpenCode 的 `bash.ts` 通过设定一个 `MAX_METADATA_LENGTH = 30_000` 甚至引入截断组件，实时裁剪超限日志 `preview(output)`。并在子进程抛错（ Exit Not 0 ）时，自动抓捕堆栈作为 `ToolResultPart` 原路压回给 Agent，催化其重试纠错反应。

## 💡 实战案例：如何优雅利用 CLI / Bash 增强 Agent

如果你是一个架构师，绝大多数情况你不应当给普通 Agent (`explore` 或受限员工级 `plan` 模型) 完全的 Bash 权限。

**最佳 Harness 实践：使用内置/注入特定的 CLI 别名而非放归野外**

假设你想让 Agent 可以部署代码到远端服务器。
错误做法：开放无限期的根目录 SSH 及全权限 Bash。导致极高安全隐患。
正确做法：在你的系统挂载一个自封装的安全脚本（例如公司私有的 `./deploy.sh`，并在其中硬编码一切环境鉴权）。
然后将 Agent 的权限墙 (`Agent.Info.permission`) 中的 Bash 功能仅限定 `allow` 这个固定的 CLI 命令字（或直接像 1.3 章节那样，不要用 Bash Tool，而是**手写一个 `ShipToCloudTool` Zod 插件套件**来将该脚本接口化）。

**一句话总结：OpenCode 处理 Bash 是极为严谨复杂的。它不仅通过 `tree-sitter` 在编译器层面拆解了危险动作，还具备完善的堆栈自动回弹机制。只要合理收敛 Permission，这柄双刃剑就能斩落一切需要手工输入的脏活累活。**
