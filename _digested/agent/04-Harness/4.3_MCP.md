# 4.3 动态能力拉取：MCP (Model Context Protocol)

如果说 Skill 是静态贴在墙上的工作守则，**MCP (Model Context Protocol)** 则是让 OpenCode Agent 连入整个世界（数据库、云监控、API 网关）的动态神经末梢。
Anthropic 倡导了这一套服务间模型上下文通信标准，而 OpenCode 在其核心系统中对它进行了原生支持。

## 🔬 OpenCode 是怎么做的？

在 `packages/opencode/src/session/prompt.ts` 中，当 Agent 接收到含有 `resource` 类型的数据块时，它不会去解析它，而是调用 MCP：
```typescript
const { clientName, uri } = part.source;
const exit = yield* mcp.readResource(clientName, uri).pipe(Effect.exit);
```

**MCP 为 Harness 带来的架构红利：按需拉取 (Pull-Based Context)。**
如果你的系统极为庞大（比如有上百个微服务的 Swagger 接口，或者实时的 Kubernetes 日志），你不可能全部塞给 System Prompt，这会让 Token 瞬间撑爆。
通过 MCP，大模型只需要知道：“系统里有一台提供架构图件和实时日志的服务器”，大模型会在它**觉得需要的时候**，主动去读一个 URI。

## 💡 实战案例：云资源检查 MCP

假设我们开发了一个本地跑在 `:3000` 的 MCP Server 叫 `AWS-Logs-MCP`。
它暴露了一个资源叫 `observability://aws/lambda/errors/today`。

如果我们在 OpenCode 配置文件中注册了这个 MCP Server。在大模型遇到如下需求时：
**用户：** “查一查今天的发版日志，并分析出导致 Lambda 挂掉的报错，顺便在这个目录下帮我写个修补。”

**大模型（内部流转）：**
1. 大模型不会写一堆没用的 bash 去 curl 网站。
2. 它意识到自己有 MCP 资源 `AWS-Logs-MCP`。
3. 它在 Loop 中向系统发起一个 `mcp.readResource` 的请求（通过特定的 Tool 或资源解析块）。
4. OpenCode 引擎去查询该 URI，此时，哪怕获取到了 20MB 的堆栈日志。这堆数据作为一坨 `synthetic: true` 的 `parts` 挂回了 `runLoop` 中。
5. 模型拿到精准报错后，马上调用内部的 `bash` 或 `edit` 工具生成修复代码。

这种解耦，做到了大模型端（思考脑）与私有化数据接口（外置资源库）的完美拆分。不需要给 LLM 泄露私钥或各种网络认证方式，底层 MCP 适配层统统包办。
