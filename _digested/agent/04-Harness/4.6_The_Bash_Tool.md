# 4.6 原生执行环境：Bash Tool 与生命周期全景追踪

你提出了一个非常通透的疑问：“大模型从看到 User 需求，到脑海里冒出想要写一段代码（Bash / Python），再到交给系统去跑，最后拿到包含结果的完整链路到底是怎么串起来的？”

为了回答这个问题，我梳理了 OpenCode 极其底层的四份核心源码：`prompt.ts`、`processor.ts`、`tool.ts`、`bash.ts`。我们来像追踪一枚子弹一样，**完整还原一整个大模型利用 Bash 解决问题的生命周期 (End-to-End Lifecycle)**。

## 🔍 代码溯源：四个不可跨越的生死门

为了证明这种极高质量的工程绝不是胡编乱造，你可以顺着这四份源码的这个闭环往下看，它们构成了一个能把大模型的野蛮能力关在笼子里的最强“枷锁”。

### 门 1: 回路引擎的分派 (`prompt.ts`)
在 `packages/opencode/src/session/prompt.ts` 中，`runLoop` 会不停止息地提取大模型想要执行的 `ToolCall`，这并不是结束，而是一场测试代码生命力的开始。模型给出的，只是一个满是未知安全漏洞和执行语法错误的 `bash` 字符串。

### 门 2: 沙箱 Zod 强卡点 (`tool.ts`)
在 `packages/opencode/src/tool/tool.ts` 大约第 62 行，任何工具被拉起前，必须先经过 Zod 拦截。
模型如果不小心把参数生成成了 `{"script": "rm -rf"}`，Zod 会当即捕获，立刻向模型扔一句“你的字段叫 script，但我期望的是 command，重写一遍。”模型在此处便会因为恐惧“自愈”生成正确的键值。

### 门 3: 最强编译器级物理截断 (`bash.ts`)
这也就是你在看 4.6 这一节的核心：它不相信模型输出的代码！
在 `packages/opencode/src/tool/bash.ts` 中，它引用了 `tree-sitter` (AST 代码解析器)：
```typescript
const root = await parse(params.command, ps);
const scan = await collect(root, cwd, ps, shell);
```
它通过遍历 AST 节点结构，彻底分析出了这行代码到底摸了系统中哪些文件目录 (`scan.dirs`)，如果发现大模型在碰危险区，它将在 `ctx.ask` 中活活把进程阻断锁死（Suspend），除非得到人类（Human-in-loop）首肯或具有顶级执行配置，这行代码注定无法拉起底层 `child_process.spawn`。

### 门 4: 收回与兜底 (`bash.ts`)
大模型敲的代码肯定会翻车（比如权限不足、找不到包）。
在 `bash.ts` 中，当 `spawn` 的真实产物跑飞掉时，哪怕它超限了几万个词或者抛出极其恶心的 Node 异常，底层的 `Truncate` 截断和异常捕获会安静拦截，并打上 `<bash_metadata>` 或 `ToolResultError` 发回原路。
带着这些“红字报错”重新喂回大模型时...在下一场死循环中，模型神奇地顿悟了：“哦，我刚才没传参数，我现在加上”。

**总而言之：**大模型只是极其聪明地产生了一个“写代码解决问题的主意”，但它在敲下这行代码直到最终看到运行结果的黑箱之旅中，**OpenCode 就像一层厚厚的套管，将不可控的 LLM 完全驯化成了可靠的工业机器手臂。**
