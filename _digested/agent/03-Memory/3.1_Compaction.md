# 3.1 上下文压缩主线：Compaction 的触发、执行与续跑

## 源码是什么 (Source)
- `packages/opencode/src/session/compaction.ts`
- 协同源码：
  - `packages/opencode/src/session/prompt.ts`
  - `packages/opencode/src/session/message-v2.ts`
- 关键符号：
  - `SessionCompaction.create/process/prune`
  - `processCompaction({ auto, overflow })`
  - `MessageV2.filterCompacted(...)`
  - `MessageV2.toModelMessages(..., { stripMedia: true })`

## 解读是什么 (Interpretation)
Compaction 是会话层的“记忆再组织机制”，不是简单摘要。

1. 触发入口有两类
- 运行时 overflow 判定后，`runLoop` 会创建 `compaction part`。
- 也可由显式流程创建 compaction user message。

2. 执行阶段使用专用 agent
- `processCompaction` 会创建 `mode=compaction` 的 assistant message（`summary=true`）。
- 给 compaction 模型注入固定摘要模板，要求输出可续跑的结构化摘要文本。

3. overflow 模式会先降载再压缩
- 通过 `toModelMessages(..., { stripMedia: true })` 剥离媒体内容。
- 需要时启用 replay 切点：压缩后回放关键 user 语义，保证后续还能继续执行。

4. 历史裁断依赖 `summary` 边界
- 后续 `filterCompacted` 会在命中完成的 summary 边界后停止回溯。
- 老历史被摘要替换为高密度上下文，而非继续全量回放。

5. 失败路径可显式 stop
- 若 compaction 自身仍超限，会写 `ContextOverflowError` 并返回 `stop`，避免无限压缩循环。

## implication 是什么 (Harness Implication)
- Compaction 是“可继续性优先”的记忆系统：目标是让任务继续，不只是削 token。
- 在大附件或高噪声项目中，`stripMedia + replay` 是恢复稳定性的关键组合。
- 若做企业私有扩展，建议把 compaction 视为一级运行时能力，而不是离线清理脚本。
