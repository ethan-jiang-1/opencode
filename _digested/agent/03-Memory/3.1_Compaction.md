# 3.1 上下文压缩与记忆控制 (Context Compaction)

作为常驻系统（Daemon-like）的 Agent，如何防止和用户的长程对聊将 Context Window（上下文窗口词元池）挤爆，是一个生死存亡的问题。

这是 `packages/opencode/src/session/compaction.ts` 提供的一个惊艳特性，也是这套架构里最具“高阶魔法”气息的部分：它用一个不可见的 Agent 洗刷另一个 Agent 的记忆。

## 🕵️‍♂️ 揭秘黑箱：幻影探员 (The Hidden Compaction Agent)

传统的防 Token 爆炸策略不外乎两种：滑动窗口机制（直接切掉头部的老消息）和 暴力计算总结（塞一段提示词叫大模型总结前文）。
前一种粗暴丢失业务状态，后一种很难维持状态一致性。

在 OpenCode 中，采取了极其优雅的第三条路：**`hidden: true` 的二级智能体截断术**。

1. **自动感知溢出**: 在每一次 `runLoop`（前文所描述）完成动作后，系统底层会触发一个副作用检测 `isOverflow(...)`。如果当前未压缩的 Token 数量碰到了预设水位线（基于具体的模型容量会有不同）。
2. **切入隔离沙箱**: 主循环会向系统的 `Processor` 丢入一个异步的后处理层。在这里，它召唤了一个名字叫 `compaction` 的内置 Agent。这套系统的天才之处在于：这个 Agent 的 `hidden: true` 意味着所有的外层 UI (如控制台或网页端) 对它是**不可见的**，用户不会看到一段奇怪的话突然插进对话流。
3. **萃取 `summary` 节点**: 这个隔离的系统只带一个使命。它通过专属的 `compaction.txt` System Prompt 去凝视那一长串几十回合的历史长河。在短暂的推理后，它只返回一段纯文本摘要，而在底层的数据库里，这个消息记录被系统牢牢打上了 `summary: true` 的布尔值标记。

## 🗡 截断树 (The Pruning Mechanism)

现在最精彩的部分来了。当下一次用户发言，`runLoop` 被重新唤醒时：

它是如何拉取前情提要的呢？
它调用了 `MessageV2.filterCompacted`！你可以把它想象成时间旅行的回溯扫描。这个扫描器从最新时间点往回走，一行行读取消息，一旦它撞到一条携带有 `summary: true` 标记的 `AssistantMessage`，扫描器立刻执行 `break`（立刻截断停止）！

这代表着那个被 `compaction` 处理的单点以上的几十上百万字噪音，**永远消失在了给主线大模型的上下文视野里**。而大模型只看见了唯一残存下来浓缩版的“精华提示词”。

## 💡 对于开发 Harness 的高级启示

这种设计，其实给了我们做长时重型架构搭建极其宝贵的思路灵感：我们可以在我们的 Harness 中复用这个状态。

如果你想写一个能够一次性扫描百万行超级工程代码，或者吞下几 MB 的报错日志的增强框架，唯一的解法就是去**模仿 `Compaction` 的哲学**。

不要让主力模型（如 `build` 或 `plan`）长期待在那段海量信息的对话分支里挨冻。使用 `Subagent` 建立平行的隔离子树，让小模型在那个子树里执行提取摘要的脏活。完成后返回带着特定标记极小的一句话推给主树干。这是当前 AI 能力边界内**最优的系统级 Context 管理**范式。
