# 3.2 截骨疗毒与垃圾回收 (Prune & Truncate)

## 📖 核心认知：被 Bash 洪水淹没的世界

在了解了 `3.1` 中伟大的幽灵压缩探员后，不要急着庆贺。因为我们在使用智能体开发系统时，最经常导致模型爆仓瘫痪的往往不是你们之间互相聊了什么，而是**工具调用产生的海量流输出（Garbage Logs）**。

例如：
1. 模型运行了 `grep -r "test" .` ，结果没有过滤 `node_modules`，终端狂飙出几百万字。
2. 模型运行了 `npm run build` 去试着构建项目以查明 Bug 的源头，然后 Vite 或 Webpack 吐出了几十兆字节连篇累牍的压缩报错堆栈。

如果我们把这种原汁原味的东西带着原路返回给 `processor.ts` 去记录，别说大模型崩不崩溃，你这台电脑的 Node.js 内存直接就爆了 `OOM`。
由此，我们需要了解在 `03-Memory` 中最后两道护城河：**历史记录垃圾清理 (Prune)** 机制以及 **执行口封锁 (Truncate)**。


## 🔍 代码溯源：`PRUNE_PROTECT` 强行阻断雪崩

我们来翻开 `compaction.ts` 里那段最容易被人忽略、但是价值极高的一条 GC (Garbage Collection) 清洗代码片段，这段代码解释了为什么系统总能稳定运行：

> **`packages/opencode/src/session/compaction.ts - prune()`**
>
> ```typescript
> // 系统定义的两条物理红线：最少榨出两万，平时死保四万。
> export const PRUNE_MINIMUM = 20_000
> export const PRUNE_PROTECT = 40_000
> // 免死金牌，绝对不能被删的东西：例如硬性强加在模型身上的公司规章制度 (skill)
> const PRUNE_PROTECTED_TOOLS = ["skill"]
> 
> const prune = Effect.fn("SessionCompaction.prune")(function* (input) {
>   // 1. 寻找当前对话底下的所有层级包
>   const msgs = yield* session.messages(...)
>   
>   let total = 0
>   let pruned = 0
>   const toPrune: MessageV2.ToolPart[] = []
> 
>   // 2. 极其粗暴且有效的“倒序回访算法”
>   loop: for (let msgIndex = msgs.length - 1; msgIndex >= 0; msgIndex--) {
>     const msg = msgs[msgIndex]
>     
>     // ... 扫描工具里产生的内容。如果这个工具是已结束的状态：
>     if (part.state.status === "completed") {
>       if (PRUNE_PROTECTED_TOOLS.includes(part.tool)) continue // 放行
>       
>       const estimate = Token.estimate(part.state.output) // 估算这条日志有多大垃圾
>       total += estimate
>       
>       // 3. 超过容忍红线！
>       if (total > PRUNE_PROTECT) {
>         pruned += estimate
>         toPrune.push(part) // 标记为该杀！
>       }
>     }
>   }
> 
>   // 4. 执行清场！只要超过了低保线 20_000，立刻物理抹除这些早已不需要反复回忆的工具执行日志
>   if (pruned > PRUNE_MINIMUM) {
>     for (const part of toPrune) {
>       part.state.time.compacted = Date.now() // 盖下死亡印记退出
>       yield* session.updatePart(part)
>     }
>   }
> })
> ```

为什么是从后往前遍历（`msgIndex = msgs.length - 1`）？
因为这是一种**反向保护机制**。最远处的古老工具回显对于后续开发来说早已成废话；而在眼前这三五轮内的工具吐字则是模型当下的短期记忆。反向数到 `40,000 Token` 相当于在脑后拉起一道绝对屏障，前面所有的老旧废料不管它多珍贵，必须为了系统能跑下去而全盘斩首。

而这个逻辑与底层 `tool/truncate.ts` 在每次刚接到流的时候就立刻做**腰斩截断 (留下头尾几十行排错信息，中间几十页的进度条全斩断)**，形成了一里一外的绝对双向防御。

## 🛠 实战落地：在自定义工具防线中怎么抄这套体系？

很多开发者在二次开发带有外部 CLI（比如 `docker build` 后端挂载）或者是拉取几千行的 SQL 数据时，常常会导致大模型失忆或者拒绝响应。

你在看完 OpenCode 的 GC 机制后，在你的 `.opencode/tools/your_cli.ts` 里面应该怎么做？

答案是：千万不要直接拿来 `execSync(cmd).toString()` 然后一股脑扔回去给主干线：
由于你掌握了这套系统架构知识，你可以手动调用引擎内的 `truncate`，并且给你的结果加上 `truncated: true` 的标志词汇。这等于你在把一块生化脏东西丢进大模型的脑回沟之前，已经通过截骨手术削干净了它。

模型之所以能够跑的远，绝对不是因为模型自身算力高，而是大后台这几道粗暴、野蛮但是极度可靠的裁剪大剪刀在为其开路！
