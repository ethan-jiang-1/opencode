# 2.4 失败自愈调度器：`retry.ts` 的重试判决面

## 源码是什么 (Source)
- `packages/opencode/src/session/retry.ts`
- 关键符号：
  - `delay(attempt, error?)`
  - `retryable(error)`
  - `policy({ parse, set })`
  - 常量：`RETRY_INITIAL_DELAY`, `RETRY_BACKOFF_FACTOR`, `RETRY_MAX_DELAY_NO_HEADERS`

## 解读是什么 (Interpretation)
这套重试不是“无脑指数退避”，而是“带协议语义的重试调度”：

1. 延迟时间优先级
- 先看 `responseHeaders["retry-after-ms"]`
- 再看 `responseHeaders["retry-after"]`（秒值或 HTTP date）
- 都没有才回退到指数退避。

2. 强硬的上限裁剪
- 所有 wait 都经过 `cap(...)`，防止 `setTimeout` 溢出或被恶意 header 拖死。

3. 错误分类是“可重试语义”而不是“异常类型语义”
- `ContextOverflowError` 明确不重试。
- `APIError` 要求 `isRetryable=true` 才重试。
- 会识别 provider 侧 JSON 错误体（`too_many_requests`、`rate_limit`、`exhausted`、`unavailable`）。

4. 调度策略通过 `Schedule.fromStepWithMetadata` 动态生成
- 每次 step 都能读取当前 attempt 与错误。
- 命中可重试时，调用 `opts.set({ attempt, message, next })` 回写状态（可用于 UI 展示“第几次重试、下次时间”）。

## implication 是什么 (Harness Implication)
- 想要“可观测重试”，不要在外层包 `try/catch + sleep`，而要把重试信息纳入同一调度状态流。
- 网关/代理接入时，优先保证 `retry-after-ms` 或 `retry-after` 头规范输出，能显著减少抖动。
- `ContextOverflow` 不重试是对的：该走 compaction，不该让重试放大 token 成本。
