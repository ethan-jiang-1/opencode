# 2.13 ProviderTransform：消息净化链与参数路由层

## 源码是什么 (Source)
- `packages/opencode/src/provider/transform.ts`
- 协同调用：
  - `packages/opencode/src/session/llm.ts`（`transformParams -> ProviderTransform.message(...)`）
- 关键符号：
  - `message(msgs, model, options)`
  - `normalizeMessages(...)`
  - `unsupportedParts(...)`
  - `applyCaching(...)`
  - `providerOptions(model, options)`
  - `schema(model, schema)`

## 解读是什么 (Interpretation)
`ProviderTransform` 是“发请求前最后一道兼容编排层”。

1. 消息先做 provider 定向净化
- Anthropic/Bedrock：过滤空 content 与空 text/reasoning part。
- Claude/Mistral：重写 `toolCallId` 为 provider 可接受格式。
- Mistral 额外修复消息序列（`tool -> user` 中间补 assistant “Done.”）。

2. 输入模态与模型能力做硬校验转换
- `unsupportedParts` 会把模型不支持的 image/audio/pdf 输入改写成错误文本提示。
- 空图片 base64 会被显式标记为损坏输入。

3. 缓存与推理参数按 provider 规则注入
- `applyCaching` 只给关键 system/final 消息打 cache control。
- `options(...)` 会按 provider 写入默认参数（如 `store=false`、`promptCacheKey`、`thinkingConfig`）。

4. providerOptions 有“网关双命名空间”路由
- 普通 provider：`{ [sdkKey]: options }`
- gateway：拆成 `gateway` 与上游 slug（如 `anthropic/openai/bedrock`）两层。

5. 工具 schema 也在这层做兼容修正
- Gemini 分支会清洗 enum/required/items 等结构，避免 provider 拒绝 schema。

## implication 是什么 (Harness Implication)
- 多 provider 稳定性的核心不在 prompt，而在这类“请求前变换层”。
- 新模型接入若出现 4xx 协议错，优先在 ProviderTransform 增补兼容分支。
- 把 schema/option/message 都收敛在同一层，能显著降低上层业务复杂度。
