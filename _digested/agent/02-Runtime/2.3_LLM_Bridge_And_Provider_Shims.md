# 2.3 LLM 桥接层：`llm.ts` 的 Provider 异构驯化

## 源码是什么 (Source)
- `packages/opencode/src/session/llm.ts`
- 关键符号：
  - `LLM.stream(input)`
  - `resolveTools(...)`
  - `hasToolCalls(...)`
  - `experimental_repairToolCall(...)`
  - `Plugin.trigger("experimental.chat.system.transform" | "chat.params" | "chat.headers")`

## 解读是什么 (Interpretation)
OpenCode 的 `LLM.stream` 不是单纯把 `messages` 丢给 SDK，而是一个“模型兼容编排层”：

1. System Prompt 组装是两阶段并可被插件改写
- 先拼接：`agent.prompt` 或 provider 默认 prompt + runtime system + user.system。
- 再触发 `experimental.chat.system.transform`。
- 如果 header 未变化，会把后续段合并，保留 2 段结构，兼顾缓存命中。

2. 采样参数不是固定值，而是四层 merge
- `ProviderTransform.options`（或 small options）
- `input.model.options`
- `input.agent.options`
- `variant`（模型变体）
- 最后再给 `chat.params` hook 二次覆写。

3. 请求头与参数也有 hook 注入位
- `chat.headers` 可注入自定义 header。
- OpenCode provider 会额外打 `x-opencode-*` 追踪头。

4. Tools 会被权限与用户开关双重过滤
- `resolveTools` 用 `Permission.disabled(...)` + `user.tools` 做最终裁剪。

5. 有一个很关键的 LiteLLM 兼容垫片
- 某些代理要求：历史里有 tool-call 时，`tools` 参数必须存在。
- 如果当前无工具，但历史有工具记录，则注入 `_noop` 假工具防止网关拒绝。

6. GitLab Workflow Model 走独立桥接
- 给 workflow model 填 `systemPrompt`。
- 注入 `toolExecutor`，把 workflow 的 tool call 转回 OpenCode 工具系统执行。

7. Tool-call 自愈策略并不依赖模型“聪明”
- `experimental_repairToolCall` 优先修正大小写（如 `Read` -> `read`）。
- 仍失败就强制转发到 `invalid` 工具，避免流直接崩溃。

8. middleware 在 provider 入参前做最后一跳改写
- `transformParams` 中调用 `ProviderTransform.message(...)` 对 prompt 进行 provider 级重写。

## implication 是什么 (Harness Implication)
- 真正做企业级 Harness，不该在 `prompt.ts` 里硬写 provider 分支；应优先落在 `llm.ts` 这层“异构兼容总线”。
- 新接一个代理网关时，先看是否需要 `_noop` 这类“协议垫片”，否则会出现“本地正常、线上代理 400”的隐性故障。
- 如果你想做全局审计、追踪、动态温度调节，`chat.params` / `chat.headers` 是稳定切入点。
- 当模型经常 tool-call 拼错，优先做 `repair` 规则，不要把“请严格遵守工具名”留给 prompt。
