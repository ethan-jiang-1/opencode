# 2.2 Processor：流事件到会话状态的转换器

## 源码是什么 (Source)
- `packages/opencode/src/session/processor.ts`
- 协同源码：
  - `packages/opencode/src/session/llm.ts`
  - `packages/opencode/src/permission/index.ts`
  - `packages/opencode/src/session/summary.ts`
- 关键符号：
  - `DOOM_LOOP_THRESHOLD = 3`
  - `handleEvent(...)`
  - `ctx.needsCompaction`
  - `cleanup()/abort()/halt()`
  - `process(...) -> "continue" | "stop" | "compact"`

## 解读是什么 (Interpretation)
Processor 负责把 LLM stream 的细粒度事件，落成 MessageV2 的可追踪 part。

1. 事件驱动写入
- `text-*`、`reasoning-*`、`tool-*`、`finish-step` 都有明确分支。
- 每个分支更新对应 part/message，而不是拼字符串。

2. Doom loop 在工具调用层做物理拦截
- 连续 3 次同工具、同输入命中后触发 `permission.ask({ permission: "doom_loop" })`。
- 防线放在 runtime，不依赖提示词“请不要重复”。

3. 压缩触发在 processor 内闭环
- `finish-step` 根据 token 与模型窗口做 `isOverflow(...)` 判定。
- 命中后设置 `needsCompaction = true`，上层 loop 收到 `compact` 分支。

4. 清理与中断语义完整
- 无论错误/中断，`cleanup()` 都会补全未结束 part、收口 tool 状态。
- `blocked/error/aborted` 会统一回传 `stop`，避免主循环误继续。

## implication 是什么 (Harness Implication)
- Processor 是最关键的“真实状态层”，可审计和可恢复都依赖这里。
- 风险控制（doom loop、overflow）应落在该层，不应放在 prompt 层赌概率。
- 做 provider 适配时，先保证事件语义对齐 Processor 的分支契约。
