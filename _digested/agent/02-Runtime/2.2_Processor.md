# 2.2 大模型交互层 (Processor Engine)

在 OpenCode 中，最脏乱差的活儿——和几十种完全不同的大模型后端（OpenAI, Claude, Ollama 等）对话，同时还需要将它们的输出强行“拉正”为系统内部的标准化工具执行流——全是由 `packages/opencode/src/session/processor.ts` 完成的。

如果说前面的 `runLoop` 是调配资源的指挥中心，那这里就是直面 AI 这匹脱缰野马的战场。

## 🎬 核心机制解析

当你通过 `runLoop` 传递了一大堆文本和 Tools 设定，模型是如何消化这些东西的呢？

Processor 的本质是一个生命周期包装器（Lifecycle Wrapper）。

1. **`create` 句柄**:
   它通过 `SessionProcessor.create`，将原本松散的单次 LLM 发文流 (Stream) 紧紧绑定在一个含有中断机制和状态锁的执行句柄 (`Handle`) 上。

2. **流拦截黑魔法 (Stream Interception)**:
   不同大模型在生成 JSON 格式以调用 Tool 的时候，返回逻辑千奇百怪。
   通过 `process` 函数底层的 `onTextContent` / `onToolCall` 等流式钩子，这里屏蔽了模型的噪音。
   最精彩的地方在于：**当模型流式生成了一段工具调用 JSON 时，它并不会等待整个大模型的输出完全结束再去动作**，它能迅速将合法的请求封存入 `ToolCallPart`。

3. **异常处理的艺术 (Error Strategy)**:
   假如模型在一个需求里擅自调用了一个不存在的 Tool 或者少传了必填的 Zod 参数。
   普通的套壳软件直接 Crash，但在这里，`MessageV2.ToolResultError` 会立刻将其包裹。
   此时的 Processor 相当于做了一个退款动作，直接向 LLM 说：“这个函数签名错误，请根据这些 Validator 提示**重写一遍**。”系统连外部都不会抛错，整个事情在这段底层的函数空间里内聚地消化掉了。

## 🎯 Structured Output 的强制绑架

针对要求模型进行严格知识推理的任务，例如我们只允许它输出一段特定的 JSON 配置，系统在这里做了个强行夹击（降维打击）：
在 `prompt.ts` 将所有 Tools 灌入的时候，如果它判断出当前的期望 `Format` 是 `json_schema` 格式，它会自动挂载一个伪劣工具 `StructuredOutput` 并将模型参数设为 `toolChoice: "required"`。
这是目前市面上最稳定提取结构化数据的做法，即使大模型能力稍弱，也能被这个 “Required” 迫使产出完全符合系统约束的字典。

## 💡 Harness 启示

如果你的 Harness 设计涉及与极其不稳定的“本地小参数模型”或者高度实验性的 API 交互，**你无需重写或污染 Processor**。它内部通过 `@ai-sdk` (Vercel) 和底层 `Effect` 的封装已经为你搞定了一切容错机制。你只需要向外抛出被正确注册并具有 Zod 参数强校验的工具即可。大模型越“笨”，它就越容易被这套严酷的边界拉回正常的轨道。
