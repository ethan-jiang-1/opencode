# 2.8 SessionProcessor：中断、清理与停机判决面

## 源码是什么 (Source)
- `packages/opencode/src/session/processor.ts`
- 关键符号：
  - `cleanup()`
  - `halt(e)`
  - `abort()`
  - `process(streamInput)`
  - `Result = "compact" | "stop" | "continue"`

## 解读是什么 (Interpretation)
`processor.ts` 不是“只消费流事件”，它还承担一次响应周期的“收尾事务”。

1. `cleanup()` 负责把半途状态收束成可审计状态
- 若 `snapshot` 还在，会补一次 `snapshot.patch(...)` 并落 `patch part`。
- 若 `currentText/reasoningMap` 尚未 `end`，会补 `end time` 并写回。
- 所有未完成的 tool part（pending/running）会被改写为 `error: Tool execution aborted`。

2. `halt()` 把错误分为两类
- `ContextOverflowError`：不标记 assistant 失败，改为 `needsCompaction=true` 并发布错误事件。
- 其他错误：写入 `assistantMessage.error`，发布 `Session.Event.Error`，并把 status 设为 `idle`。

3. `abort()` 与 `cleanup()` 的关系是“条件式调用”
- 如果尚未标记 error，会先注入 `AbortError` 走 `halt()`。
- 如果消息尚未 completed，会执行 `cleanup()`，避免脏状态留存。

4. `process()` 的执行链路是“流处理 + 重试 + 保底清理”
- 流事件经 `handleEvent`，同时受 `Stream.takeUntil(() => ctx.needsCompaction)` 控制。
- 外层套 `SessionRetry.policy(...)`，并在中断时打 `aborted=true`。
- 无论成功/失败/中断，都会 `Effect.ensuring(cleanup())`。

5. 最终返回值把控制权交回 `runLoop`
- `needsCompaction` -> `"compact"`
- `blocked` 或 `assistantMessage.error` 或 `aborted` -> `"stop"`
- 否则 -> `"continue"`

## implication 是什么 (Harness Implication)
- 外部扩展若监听 message part，必须接受“同一 part 在 cleanup 阶段被二次改写”的事实。
- 取消请求应优先走 `abort()` 语义，而不是只杀进程；否则会丢失会话一致性。
- 溢出要走 compaction 通道，不应和普通错误混在同一个恢复策略里。
