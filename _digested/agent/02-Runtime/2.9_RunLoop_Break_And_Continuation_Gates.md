# 2.9 `runLoop`：主循环的 break/continue 闸门系统

## 源码是什么 (Source)
- `packages/opencode/src/session/prompt.ts`
- 关键符号：
  - `runLoop(sessionID)`
  - `tasks.pop()`（`subtask/compaction` 优先处理）
  - `compaction.isOverflow(...)` 与 `compaction.create(...)`
  - `handle.process(...)` 返回 `"compact" | "stop" | "continue"`
  - `MAX_STEPS` 提示注入（`isLastStep`）

## 解读是什么 (Interpretation)
`runLoop` 的核心不是“循环”，而是“分支顺序”。

1. 每轮先做状态扫描，再决定本轮执行类型
- 逆序扫描消息流，提取 `lastUser/lastAssistant/lastFinished/tasks`。
- 若最近 assistant 已完成且不是 `tool-calls`，并且其在最新 user 之后，直接退出循环。

2. 任务优先级是固定的
- 优先执行 `subtask`（`handleSubtask`），然后 `continue`。
- 其次执行 `compaction part`（`compaction.process`），然后根据结果 `continue/break`。
- 两者都没有时，才进入常规 LLM+Tool 推理。

3. 常规推理前有自动溢出闸门
- 若 `lastFinished` 已超窗口且非 summary，会先创建自动 compaction，再开新一轮。

4. 每轮 assistant 都是新消息节点
- 新建 assistant message -> `processor.create(...)` -> `resolveTools(...)` -> `handle.process(...)`。
- 若达到 agent 步数上限，只是给模型追加 `MAX_STEPS` 提示，不是立即硬中断。

5. `process` 结果决定主循环方向
- `"stop"`: break
- `"compact"`: 追加 compaction 任务后 continue
- `"continue"`: 下一轮
- 若捕获结构化输出成功，也会强制 break。

## implication 是什么 (Harness Implication)
- 要加新阶段（如审计、策略插桩），必须明确插在哪条闸门前后，否则会打乱优先级。
- 这套顺序保证了 `subtask/compaction` 不与常规推理竞争同一轮执行资源。
- “最后一步”依赖提示约束而非硬 kill，意味着外部系统仍应准备兜底超时策略。
