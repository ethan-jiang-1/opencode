# 2.10 Runner 单飞控制：每会话唯一执行通道

## 源码是什么 (Source)
- `packages/opencode/src/session/prompt.ts`
- 关键符号：
  - `InstanceState.make({ runners: Map<sessionID, Runner> })`
  - `getRunner(...)`
  - `assertNotBusy(sessionID)`
  - `loop(...) -> runner.ensureRunning(...)`
  - `shell(...) -> runner.startShell(...)`
  - `cancel(sessionID) -> runner.cancel`

## 解读是什么 (Interpretation)
`SessionPrompt` 在服务层做了“每 session 单飞 (single-flight)”。

1. runner 以 `sessionID` 为 key 缓存
- 同一会话复用同一个 `Runner`，避免并发 prompt/shell 互踩。

2. busy 生命周期是 Runner 回调驱动
- `onBusy` -> `status.busy`
- `onIdle` -> 清理 runners map + `status.idle`
- `onInterrupt` -> 回退到 `lastAssistant(sessionID)` 作为最终返回

3. 对外入口都走 runner
- `loop` 不直接跑 `runLoop`，而是 `ensureRunning`。
- `shell` 走 `startShell`，与普通对话共享同一互斥面。

4. 并发拒绝有显式错误类型
- `assertNotBusy` 和 `runner.busy` 路径都会抛 `Session.BusyError`。

5. cancel 是语义化取消
- 空闲会话直接标 idle。
- 忙会话触发 runner.cancel，交给内部中断与 cleanup 完成收尾。

## implication 是什么 (Harness Implication)
- 多端（CLI/IDE/Web）同时操作同一 session 时，这层是防重入的硬护栏。
- 任何新入口若绕过 runner，都会破坏 busy/idle 一致性。
- 外部 orchestration 做排队时，可把 `BusyError` 当成“可重试拥塞信号”。
