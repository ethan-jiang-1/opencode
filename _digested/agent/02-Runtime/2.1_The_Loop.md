# 2.1 The Loop：模型引擎的生死循环

## 📖 核心认知：`while(true)` 的秘密与并发编排

“智能体”（Agent）这个词非常抽象，如果说 01 分区我们看了这具骨架的数据结构，那么在 `02-Runtime` 区域里，我们要解答的是：到底怎样的一串代码让这些“数据”变成了能读你需求、能思考、能敲代码的“脑？”

在 `packages/opencode/src/session/prompt.ts` 里，有一个极其凶残但也极其华丽的“循环心脏”机制。模型一旦接收到任务，就会掉入这个循环中，直到它说：“我做完了”，或是超出了限制，亦或它试图炸掉系统被你掐停。

---

## 🗺 架构：多探员调度的 Effect 引擎

```mermaid
flowchart TD
    User([User Request 发起请求]) --> Parse[resolvePromptParts 解析文件路径及上下文]
    Parse --> Insert[insertReminders 注入架构师提醒与系统模式]
    Insert --> Loop(进入核心 while(true) 永动机)
    
    subgraph The Heart Loop [生死主循环 prompt.ts runLoop]
        Loop --> Pull{拉取最新可用工具}
        Pull --> Gen[模型运算 generateObject / streamObject]
        Gen -. 流逝截获 ..-> Processor[Processor 中间件]
        Gen --> Eval{执行结果判断}
        
        Eval -->|生成了 Subtask| Task[抛入后台拉起新探员异步执行!]
        Task --> Update[更新 session，重新组装 Message 回收]
        
        Eval -->|生成了 ToolCall| TCall[触发 Zod 沙箱，尝试读取/书写]
        TCall --> Update
        
        Eval -->|回答完毕 (Text) 或遇到致死报错| Exit(退出死循环！)
    end
    
    Update --> Loop
    Exit --> Done([界面渲染任务完成])
```

## 🔍 代码溯源：主循环的护城河怎么建的

很多人写 Agent 就是写个 `let count = 0; while(count < maxLimit)` 就完事儿了。我们去扒一扒 `prompt.ts` 里那厚实得离谱的安全保障，了解 OpenCode 的主循环到底有多精悍。

> **`packages/opencode/src/session/prompt.ts - runLoop (摘要演示)`**
>
> ```typescript
> let maxSteps = agent.steps ?? MAX_STEPS // 根据系统默认配置限定步数，如 30 步强制熔断
> let step = 0
> 
> while (true) {
>   step++
>   
>   // 1. 每一次搏动，重新解析系统里的工具（应对那些动态拔插甚至在对话中途创建的新工具）
>   const toolMap = yield* resolveTools({ ... })
>   // 2. 将之前历史的所有对话压入（此时可能已经经历过 Compaction 降维压缩）
>   const contextMessages = yield* Effect.promise(() => MessageV2.toModelMessages(msgs, ...))
>   
>   // 3. 将控制权交给 SessionProcessor 流处理器
>   const processor = yield* processors.create(...)
>   
>   // 4. 发射网络请求
>   const result = yield* processor.process({ ... })
> 
>   // ========== 接下来是极其硬核的四重打断拦截 ==========
>   
>   // 情况A：发生了灾难级 Context Overflow，处理器要求进行降维打击压缩！
>   if (result === "compact") {
>      yield* compaction.process({ parentID: msg.id, auto: true... })
>      continue // 压缩跑完，继续循环！
>   }
>   
>   // 情况B：致命阻塞、断点、或者系统错误
>   if (result === "stop") {
>       break // 直接砸碎永动机退出
>   }
>   
>   // 情况C：用户在网页上要求 "cancel"，这是由底层 Effect Runner 从主线程发出硬中断
>   if (yield* Effect.isInterrupted) {
>       break 
>   }
>   
>   // 情况D：防暴走（超出最大步数限制）
>   if (step >= maxSteps) {
>       assistantMessage.error = `Max steps (${maxSteps}) exceeded.`
>       break
>   }
>   
>   // 情况E：它到底写了字，还是操作了工具？
>   const hasToolCalls = processor.message.parts.some(p => p.type === "tool" || p.type === "subtask")
>   if (!hasToolCalls) {
>       // 如果它没用工具而直接回答了文本，那是大功告成，退出死循环
>       break
>   }
> }
> ```

## 🛠 实战落地：并行的 Subagent 魔法

很多时候我们会诧异，为什么 OpenCode 说它能“多线程寻找答案”？因为在这套死循环里，有一种独特的工具叫做 `TaskTool`，这就是我们刚才讲到的 `subagent`（如 `explore` 或 `general`）。

**一旦循环 `Eval` 检测到你要拉起子任务：** 
由于底层完全是基于 `Effect` 的异步图谱构建（见 `makeRuntime(Service, defaultLayer)`），主循环将启动一个新的完全干结干净的 `SessionID` 给那 3 只探索者探员！主线程会在挂起状态等待它们用 `taskArgs` 吐回执行报告总结，然后再包装回当前的循环里告诉你的主模型。这就是它既快、又不会被带偏的原因。
